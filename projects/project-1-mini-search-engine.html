MSIS · AME 5053 · Unit I · Project 1

A mini search engine

Everything from sessions 1 to 10, assembled into one working system: raw newswire in, ranked results out, with a search box on top and an honest account of what each step did to the answers.

What you are building

A search engine over a collection of 10,788 news articles. A user types a query into a box in the browser; your system returns the documents that best match, in order, with the matched words highlighted, in well under a second. Behind the box sits everything Unit I taught: a regular expression that pulls structure out of raw text, a preprocessing pipeline, an inverted index, and TF-IDF ranking.

You are not being asked to invent anything. Every component was covered in a session and most were built in a lab, on six documents. The project is what happens when you assemble them, point them at a real collection, and then have to answer the question a working system always raises: which of my choices actually helped?

The shape of the work

Six stages, in order. Each one produces something you can run and check before you start the next. Stage 6 is the interface; do not start there. A search box over an index that returns the wrong documents is worth very little, and the interface carries 10 marks of 100.

Two ways to do this

The project can be built either way, and both are marked identically.

From the starter repository. It holds the collection, a command line for trying queries, the evaluation harness and a test suite, with a stub for every function you have to write. Take this route if you would rather spend your three weeks on the measuring and the writing, which is where most of the marks are.

From an empty directory. The requirements sheet is this brief written out as a plain checklist, with no code in it, plus the figures your finished system has to reproduce so that you can check yourself without the test suite. Take this route if you would rather build the whole thing, plumbing and tests included.

Neither is the harder option on paper. Building from scratch simply means the plumbing is also yours. The rest of this section describes the starter; if you are not using it, read the requirements sheet instead and rejoin at The collection.

The tests are the specification. Where this brief says a postings list must come out sorted, or that idf is base 10, or that only candidate documents may be scored, there is a test that checks it. Read a stub's tests before you write the stub — they are shorter than the prose and they are exact.

pytest                    the fast tests — a toy collection, about a second
pytest -m slow            the corpus tests; a few minutes, on the real index
pytest -m ""              both
pytest -k merge -x        one thing, stopping at the first failure

The fast tests run on the six-document collection from lab 4, where you already know the right answers, so a failure names the merge that is wrong instead of telling you the corpus is disappointing. The slow ones build the real index and check the figures quoted in this brief. Run those before you submit, and before you believe any number in your report.

One file, tests/test_yours.py, fails on purpose. Those five are yours to write, and they carry marks — see the rubric.

Do not edit the given tests

A suite that passes because you weakened it is worth nothing, and it is obvious in a diff. If you think a given test is itself wrong, say so in your report and show why. That is a reasonable claim to make about a specification and it will be read as one.

The collection

You will index the Reuters-21578 corpus, a standard collection of Reuters newswire articles from 1987. It ships with NLTK, so there is nothing to download by hand:

import nltk
nltk.download("reuters")
from nltk.corpus import reuters

fileids = sorted(reuters.fileids())   # 10,788 documents
print(len(fileids))
print(reuters.raw(fileids[0])[:200])

Two properties of this corpus matter for the project.

First, each document begins with a headline in capitals on its own line, followed by the body. That is a piece of structure sitting in unstructured text, which is what stage 1 is about.

Second, every document carries one or more topic labels — reuters.categories(fileid) returns them, from a set of 90 including crude, grain, earn and acq. These labels were assigned by Reuters, not by us, and your search engine must never look at them. They exist in this project for one purpose only: in stage 5 they let you check whether a change you made improved the results or made them worse, instead of asserting that it helped.

Everyone indexes the same documents in the same order. Use sorted(reuters.fileids()) and let document 0 be the first of that list, so that a document ID means the same thing in your submission as in everyone else's, and a claim about document 4,174 can be checked.

Stage 1 — Pulling structure out of raw text

The corpus arrives as unstructured strings. Before anything can be indexed, split each document into the fields a search result will need to display, using regular expressions (sessions 1 and 2):

  • Headline — the first line.
  • Body — everything after it, with the whitespace tidied. Reuters bodies are hard-wrapped mid-sentence; a single-spaced string is easier to snippet.
  • Money amounts — the corpus is full of them, in several shapes: 3.5 mln dlrs, 1,250,000, vs 2.1 pct. Write one expression that catches the common forms and report how many documents contain at least one.
  • Dates — the corpus writes them as March 5, MARCH 1987 and other variants. Catch what you reasonably can.

You will not catch everything, and you are not expected to. What you are expected to do is look at what you missed: pick twenty documents at random, read your extractor's output against the text, and record in your report one thing your expression gets wrong and why. Session 2's greedy trap is a good place to start looking.

A rule for the whole project

Regular expressions are for stage 1 only. Do not use one as your tokenizer — session 3 explained at some length why that fails, and stage 2 is where you use a real one.

Stage 2 — The preprocessing pipeline

Fill in one analyser that turns a string into a list of terms, with each step controlled by a field:

class Analyzer:
    def __init__(self, fold=True, drop_stop=True, stem=True, lemma=False):
        ...

    def terms(self, text):
        """Raw text in, list of index terms out."""
        ...

The steps it applies, all from sessions 3 to 5, in this order. The order is part of the specification and the docstring in pipeline.py repeats it:

  1. Unicode normalisation (NFKC) of the whole string, always — before tokenization, because a compatibility ligature has to become letters before anything can split on word boundaries. This one does not depend on the fold switch.
  2. Tokenization with NLTK's word_tokenize or spaCy, not str.split().
  3. Keeping only tokens that are all letters, with token.isalpha(). That drops punctuation and pure numerals. Keep the numbers you extracted in stage 1 — they are metadata, not index terms.
  4. Case folding, if fold.
  5. Stop word removal, using NLTK's English list. The comparison is against the lowercased token whether or not fold is set, because that list is lowercase and testing an unfolded token would silently keep every capitalised The.
  6. Stemming (Porter) or lemmatization (WordNet or spaCy). Implement both; you will compare them in stage 5.

That this is one object with switches, rather than four hard-coded pipelines, is not a stylistic preference. It is worth saying why twice over.

The rule this project is built around

The query must go through exactly the same pipeline as the documents. If the index holds opec because the pipeline folded case, and a user's OPEC reaches the index unfolded, the term is simply absent and the query silently returns nothing. Session 9 said this; it is the single most common way this project goes wrong. The index therefore keeps the analyser it was built with and calls it on every query, so the two cannot drift apart — that is what index.analyse_query() is for, and it is the one method you are given rather than asked to write.

The second reason is that stage 5 asks you to run the whole system four different ways. If the steps are hard-coded you will be editing your indexer four times and comparing runs you cannot reproduce. An analyser you can pass as an argument makes the ablation a loop.

Stage 3 — Boolean retrieval

Build both structures from sessions 8 and 9, on the same terms, and compare them honestly.

The term-document incidence matrix, first, on a 500-document subset — enough to be real, small enough to hold. Answer A AND B AND NOT C with bitwise operations on its rows, as in session 8. Then measure: how many cells does the matrix have, how many are non-zero, and how large would the matrix be over the full 10,788 documents?

Report that last number carefully, because it does not say what session 8's argument might lead you to expect. Over the full corpus the matrix is about 20,000 × 10,800 cells. Packed one bit per cell that is roughly 28 MB, which fits in memory without difficulty. The matrix does not fail at this scale. Work out where it does fail, using session 8's own numbers for a web-sized collection, and say so in your report in terms of how the cost grows rather than what it happens to be here.

The inverted index, second, over all 10,788 documents: a dictionary from term to a sorted postings list. Store the within-document count alongside each document ID — stage 4 needs it, and adding it later means rebuilding.

Implement query processing by merging postings lists, not by converting them to Python sets:

  • AND, OR and AND NOT as linear merges over sorted lists.
  • Multi-term AND with the rarest-first optimisation from session 9, processing terms in increasing document frequency.
  • Evidence that rarest-first helps: time a three-term query both ways and report both numbers.

A set() intersection gives the same answer and is genuinely fast, but it hides the merge, and the merge is what session 9 was about. Use sets anywhere else you like.

Stage 4 — Ranked retrieval

Boolean retrieval returns a set. On this corpus, crude AND oil AND opec returns 72 documents in no particular order, and nobody reads 72 documents. Add ranking, exactly as session 10 defined it.

The term frequency weight, with the count compressed:

wt,d=1+log10⁡(tft,d)

the inverse document frequency, from the postings list length:

idft=log10⁡Ndft

and the score of a document for a query, summed over the query's terms:

score(q,d)=∑t∈q(1+log10⁡tft,d)⋅log10⁡Ndft

Return the top k by that score. Two requirements on how you compute it:

  • Score only the documents that can score above zero — those appearing on the postings list of at least one query term. Walking all 10,788 documents for every query gives the same ranking and is the wrong algorithm.
  • Precompute nothing you cannot justify. Document frequency is the length of a postings list, so it needs no separate pass. Say in your report what you cached and why.

Two sanity checks before you go on. A term appearing in every document must receive idf=0 and contribute nothing to any score; construct a case and show it. And opec (df 121) must outweigh said (df 6,784) heavily — on this corpus their idf values are 1.950 and 0.201.

Stage 5 — Measuring your own choices

This stage is what separates the project from the labs, and together with the tests you write it carries nearly a third of the marks. Every decision in stage 2 was presented to you as a choice, and so far you have only been told that such choices matter. Here you find out, on your own system.

The query set

These ten queries are supplied, each paired with the Reuters topic label that a good answer ought to carry:

queryrelevant label
crude oil prices opeccrude
interest rate cut by the federal reserveinterest
wheat grain exports to the soviet uniongrain

japanese yen dollar currency interventionmoney-fx

sugar production quotasugar
shipping freight ratesship

For one query, retrieve the top ten documents and count how many carry the paired label. That fraction is precision at 10. Average it over the ten queries and you have one number describing your system.

It is a rough measure and you should treat it as one. A document about the oil price that Reuters happened not to label crude counts against you unfairly, and ten queries is a small sample. It is nevertheless a great deal better than looking at the results and deciding they seem reasonable, and it has the property that matters: it is computed the same way before and after a change, so a difference means something.

The comparison

Run your full system under each of these settings and record vocabulary size, index build time, mean query time, and mean precision at 10:

  1. Tokenization and case folding only.
  2. Plus stop word removal.
  3. Plus Porter stemming.
  4. Plus lemmatization instead of stemming.
  5. Stemming with the stop list taken back out — the run the next section needs.

These are the five entries of evaluate.SETTINGS, and python -m minisearch.cli ablate prints the table once ablation() is written.

Then write the paragraph that the table is for. Which step changed the results most? Did any step make them worse? Session 4 warned that stop word removal is sometimes a mistake and session 5 that stemming and lemmatization are not interchangeable — you now have evidence about this corpus, and evidence about one corpus is what you should claim.

What idf does to stop words

Session 10 claimed that TF-IDF suppresses common words without needing a stop list, because a word in every document has idf=0. Test that claim directly, and note what the comparison has to be: setting 5 against setting 3. Those two differ in exactly one field — one has the stop list, the other leaves the stop words in the index and lets idf deal with them — so a difference between them is attributable. Comparing against setting 1 would move stemming at the same time and tell you nothing about the claim.

While you are there, sort your vocabulary by document frequency and read the top thirty terms. NLTK's stop list was written for English in general, not for newswire, and this corpus has words that behave exactly like stop words without appearing on any list. Name one in your report, give its df and idf, and say what a stop list would have had to know in order to contain it.

Subword tokenization

Session 3 introduced BPE, and every step above has assumed a word is the unit. Train a BPE tokenizer on this corpus with a vocabulary of 8,000 and compare it with your word vocabulary:

from tokenizers import Tokenizer, models, trainers, pre_tokenizers, normalizers

tok = Tokenizer(models.BPE(unk_token="[UNK]"))
tok.normalizer = normalizers.Sequence([normalizers.NFKC(), normalizers.Lowercase()])
tok.pre_tokenizer = pre_tokenizers.Whitespace()
tok.train_from_iterator((reuters.raw(f) for f in fileids),
                        trainers.BpeTrainer(vocab_size=8000, special_tokens=["[UNK]"]))

Report three things. How many types the word pipeline needs to cover the corpus against BPE's 8,000. What BPE does to a word your word index has never seen — take a word from outside the corpus and encode it. And what the pieces look like: unbelievably comes back as un, belie, v, ably, which are not the morphemes session 3 described, and the brief explanation of why not is the point of this exercise.

You are not asked to build a second index on subword units. Say in one paragraph why subword tokens are awkward as index terms for a search engine, given what stage 4 does with document frequency.

Stage 6 — The interface

Put a Streamlit app in front of the index. A single page:

  • A search box, and a choice between Boolean and ranked retrieval.
  • Results: headline, score, topic labels, and a snippet of the body with the query's terms highlighted. The highlight must survive stemming — a search for mining should mark mines if that is why the document matched. Say how you did it.
  • A timing line: "10 results of 328 in 24 ms". The 328 is n_matching in ranked mode and the length of the postings result in Boolean mode — search_ranked hands back the slice, not the total.
  • A sidebar that switches between the stage 5 settings, so a visitor can see the ablation happen rather than read the table.

That last one has a trap in it, and noticing the trap is part of the exercise. You cannot change the analyser and search the same index: the terms in the index were produced by that analyser, so an unstemmed query against a stemmed index is exactly the mismatch stage 2 was about. Each setting needs its own index, built ahead of time. build_index.py --all does that and saves them together.

Two practical points. Load the saved indexes once, with @st.cache_resource; without it Streamlit re-reads them on every keystroke and the app is unusable. And the app should load, never build — it should start in about a second, not in the minute per setting the build takes.

The interface is worth 10 marks of 100. It should be clean and it need not be beautiful.

  • Libraries. NLTK, spaCy, regex, NumPy, tokenizers, Streamlit and the standard library. Also scikit-learn, but see below.

What is not in this project

Sessions 6 and 7 — part-of-speech tagging and named entity recognition — are deliberately excluded. So is anything from Unit II onwards: no word embeddings, no classifier, no neural network. In particular cosine similarity is not part of this project. It arrives in session 19, and ranking here is the sum of TF-IDF weights that session 10 defined. Using cosine early is not rewarded, and describing your ranking as cosine when it is a sum costs marks.
