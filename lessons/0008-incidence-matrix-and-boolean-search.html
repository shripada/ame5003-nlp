Searching a collection

The term-document incidence matrix and how Boolean queries are answered with it, together with the reason it does not scale to real collections.

Information retrieval

Everything so far, including tokenization, tagging, and named entity recognition, operated on a single piece of text. We now ask a different question: given a whole collection of documents, which of them match what we are looking for? This is information retrieval, and it is what a search engine does.

We begin with the simplest useful form of search, the Boolean query, in which documents are requested using AND, OR, and NOT. Over the plays of Shakespeare, for example:

Brutus AND Caesar AND NOT Calpurnia

This asks for the plays that contain both Brutus and Caesar but not Calpurnia. The question is how to answer it quickly over a large collection.

Scanning every document

One approach is to scan every document for the words, as Ctrl-F or the Unix grep tool does. For a single file this is adequate. For a large collection it is far too slow, since every document is re-read on every query. It also handles NOT and complex combinations awkwardly, and provides no basis for ranking results later. What we need is for the collection to be organised in advance, so that queries are fast.

The term-document incidence matrix

The first such organisation is a table with one row per term and one column per document. Each cell contains a 1 if the term appears in that document and a 0 if it does not.

For a handful of terms across six Shakespeare plays, it looks like this (1 = "the play contains this word"):

term Antony &
Cleopatra		Julius
Caesar		The
Tempest		 HamletOthelloMacbeth
Antony 110001
Brutus 110100
Caesar 110111
Calpurnia 010000
Cleopatra 100000
mercy 101111
worser 101110

Each row is now a string of 0s and 1s, a bit vector, recording exactly which plays contain that word. The Caesar row is 1 1 0 1 1 1, so the word appears in every play except The Tempest.

Answering the query with bitwise operations

Once each term is a row of bits, a Boolean query becomes bitwise arithmetic on those rows. Returning to the query:

Brutus AND Caesar AND NOT Calpurnia

We take the three rows and combine them column by column. AND retains a 1 only where both rows have a 1, and NOT inverts every bit:

Brutus            1 1 0 1 0 0
Caesar            1 1 0 1 1 1
NOT Calpurnia     1 0 1 1 1 1     ← Calpurnia was 0 1 0 0 0 0, flipped

Brutus AND Caesar             →   1 1 0 1 0 0
        AND NOT Calpurnia     →   1 0 0 1 0 0

The resulting vector is 1 0 0 1 0 0. The 1s are in columns 1 and 4, so the answer is:

Antony and Cleopatra     Hamlet

This is the entire method. Every Boolean query reduces to a few bitwise operations on the rows of the matrix, and bitwise operations are among the fastest a computer performs.

Exercise

Using the matrix above, evaluate Antony AND mercy. Which plays are returned?

Combine the two rows with AND, column by column:

Antony   1 1 0 0 0 1
mercy    1 0 1 1 1 1
AND      1 0 0 0 0 1

The 1s are in columns 1 and 6, giving Antony and Cleopatra and Macbeth. The two words occur together only in those plays.

Why this does not scale

The method itself is sound. The difficulty is the size of the table. Terms run down one axis and documents across the other, so the matrix grows with both. Consider the figures for a realistic collection:

  • 1 million documents (columns)
  • about 500,000 distinct terms (rows)

This gives 500,000 × 1,000,000 = 500 billion cells, or half a trillion 0s and 1s to store.

The decisive detail is the distribution of those values. Each document contains perhaps a thousand distinct words, so each column holds about a thousand 1s and 499,000 zeros. Across the whole matrix there are at most about a billion 1s, which means:

The matrix is almost entirely zeros

Out of 500 billion cells, at most about 1 billion are 1s. That is 99.8% zeros.

Almost all of the memory would be spent recording that words are absent from documents, a fact that is nearly always true and rarely what the query asks about. The matrix will not fit in memory, and if it did, storing it this way would still be wasteful.

The incidence matrix therefore embodies the right idea, namely organising the collection in advance so that queries are fast, in the wrong representation. The correction follows directly from the diagnosis.

Exercise

Almost every cell in the matrix is a 0, and those 0s carry no information we need. What should be changed?

Stop storing the zeros. Record only the 1s.

For each term, instead of a full row of mostly-zero bits, keep a list of the documents in which it actually appears. That list is short, because a given word occurs in few documents, and no space is spent on absence.

This structure is called an inverted index. It is the subject of session 9 and the structure built in lab 4.

Question 1 of 2

In a term-document incidence matrix, what does a single row represent?

Correct answer: one term, as which documents it appears in.

Rows are terms and columns are documents. The Caesar row, 1 1 0 1 1 1, records that Caesar appears in every play but the third. A Boolean query combines these rows with bitwise AND, OR, and NOT.

Question 2 of 2

What is the main problem with the incidence matrix at real scale?

Correct answer: it is almost all zeros, so it wastes nearly all its space.

A million documents by half a million terms gives 500 billion cells, of which at most a billion are 1s, or about 99.8% zeros. The bitwise operations themselves are fast; it is the storage of all that absence that makes the approach impractical. Recording only the 1s is the correction, and that is the inverted index.

Summary

The main points

A term-document incidence matrix reduces Boolean search to fast bitwise operations on rows of 0s and 1s, and it is correct. At realistic scale, however, it is 99.8% zeros and does not fit in memory, so the practical solution is to store only the 1s. That structure is the inverted index, the subject of session 9.
