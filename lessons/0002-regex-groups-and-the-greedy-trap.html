Capturing, choosing, and the greedy trap

Regular expressions, part two: extracting the individual pieces of a match, handling more than one input format, and understanding greedy matching.

Where session 1 left off

In session 1 we learned to describe the shape of text: \d{2} for two digits, [Cc]at for either spelling, u? for an optional character.

These patterns locate text, but locating is only half of the task. We usually also want to extract the individual pieces of a match, or to handle text that arrives in more than one format. This session covers both.

Groups

Round brackets around part of a pattern make it a group. The regular expression engine records what matched inside each group.

text     "Exam on 15/03/2026."
pattern  (\d{2})/(\d{2})/(\d{4})

whole match  ->  15/03/2026
group 1      ->  15      the day
group 2      ->  03      the month
group 3      ->  2026    the year

The groups are numbered left to right by their opening bracket. Group 0 is always the whole match.

In Python:

import regex

m = regex.search(r"(\d{2})/(\d{2})/(\d{4})", "Exam on 15/03/2026.")
m.group(0)   # '15/03/2026'
m.group(1)   # '15'
m.group(3)   # '2026'

Groups are what separate knowing that a date is present from knowing that the exam is in March.

How groups change findall

The presence of groups changes what findall returns.

text = "Due 15/03/2026 and 01/04/2026"

regex.findall(r"(\d{2})/(\d{2})/(\d{4})", text)
# [('15', '03', '2026'), ('01', '04', '2026')]   <- tuples!

regex.findall(r"\d{2}/\d{2}/\d{4}", text)
# ['15/03/2026', '01/04/2026']                   <- the dates

When groups are present, findall returns the groups rather than the whole match. To use brackets for grouping without capturing, write (?:...), a non-capturing group:

regex.findall(r"(?:\d{2})/(?:\d{2})/\d{4}", text)
# ['15/03/2026', '01/04/2026']

Alternation

The | symbol means "or".

Real data rarely arrives in a single format. Some sources write 15/03/2026 and others write 15-03-2026. A single pattern can accept both:

\d{2}[/-]\d{2}[/-]\d{4}

matches  15/03/2026
matches  15-03-2026

Here the character class [/-] suffices, since the choice is between single characters. Choices between longer sequences require | together with brackets:

(?:cat|dog)s?

on "a cat, two dogs"  ->  ['cat', 'dogs']

The brackets are necessary. cat|dogs? means "cat, or dogs?", which is not the intended reading: | divides the entire pattern unless brackets limit its scope.

Word boundaries

Consider searching for cat in the following word:

concatenate

The pattern matches. It found "cat" inside "concatenate", correctly so: we asked for those three letters, and they are present.

\b means word boundary: the edge between a word character and a non-word character. It matches a position, not a character.

pattern      concatenate    the cat sat    cat.
cat              yes            yes         yes
\bcat\b          no             yes         yes

Note the last column. \bcat\b still matches cat., since the full stop is not a word character and a boundary therefore exists between them. This is normally the desired behaviour, as we are looking for the word regardless of adjacent punctuation.

Word boundaries in Kannada

Session 1 showed that re splits Kannada words at the virama. We now examine the effect this has on \b.

In English, \bcat\b correctly declines to match inside concatenate, since "cat" is not a whole word in that context. Applying the same test to ಕನ್ನಡ, we ask whether the fragment ಕನ is a whole word:

re.search(r"\bಕನ\b", "ಕನ್ನಡ")      # matches!    ← wrong
regex.search(r"\bಕನ\b", "ಕನ್ನಡ")   # no match     ← right

re reports a match, treating ಕನ as a complete word inside ಕನ್ನಡ. It is not a word; it is the first half of one.

The reason follows from session 1. \b is defined as the edge of a run of \w characters, so if \w is wrong about where words end, \b inherits that error:

number of \b positions inside ಕನ್ನಡ

re      4      two at the ends, two invented at the virama
regex   2      just the ends — correct

The rule is identical in both libraries; it works for English and fails for Kannada. This is what "not Unicode compliant" means in practice. There is no crash, only a wrong answer returned without any indication that anything is amiss.

Where does a word end?

This example is a small instance of the question the whole unit addresses: where does a word end?

\b gives one crude answer, namely "at the edge of a run of word characters". Even with a correct library, that answer fails for don't, for U.S.A., and for languages that do not separate words with spaces at all.

A good library gives us a better wrong answer, not a right one. Session 3 considers what to do instead.

Greedy and lazy quantifiers

We now come to the most common error in writing regular expressions. Suppose we want to extract the tags from the following text:

<b>bold</b> and <i>italic</i>

A tag consists of an angle bracket, some content, and a closing angle bracket, which suggests the pattern <.*>. Running it gives:

regex.search(r"<.*>", text).group()

# <b>bold</b> and <i>italic</i>

The pattern matched the entire line, treating it as a single tag.

The reason is that * and + are greedy: they consume as much text as possible, and return characters only when the remainder of the pattern cannot otherwise match.

We can trace the process. < matches the first angle bracket. .* then consumes everything to the end of the line. At this point the pattern still requires a >, but no text remains, so .* gives back one character at a time until a > can match. The first > encountered when working backwards is the last one on the line.

Adding ? after the quantifier makes it lazy, meaning that it consumes as little text as possible:

regex.search(r"<.*?>", text).group()      # <b>

regex.findall(r"<.*?>", text)
# ['<b>', '</b>', '<i>', '</i>']
A more precise alternative to lazy matching

Lazy matching solves the problem, but there is a more precise way to express the same intent:

regex.findall(r"<[^>]*>", text)
# ['<b>', '</b>', '<i>', '</i>']

This pattern reads as "an angle bracket, then any number of characters that are not a closing bracket, then a closing bracket." It cannot overshoot, because it is never permitted to cross a >.

Being precise about what a pattern allows is preferable to correcting the result afterwards. This is the same point made by the roll number example in session 1, and it recurs throughout the course.

Question 1 of 2

On the text "aaa", what does the pattern a+? match?

Correct answer: just one letter a.

a+? should be read as two separate elements. a+ means "one or more a", and the ? that follows makes the quantifier lazy.

The pattern must therefore take at least one character, and being lazy, it takes exactly one and stops.

As with ^ in session 1, the difficulty is that ? serves two purposes. After a character, a? means "optional"; after a quantifier, +? means "lazy". Which meaning applies depends on what precedes it.

Question 2 of 2

Why does regex.findall(r"(\d{2})/(\d{4})", text) return tuples?

Correct answer: findall returns the groups when groups exist.

When the pattern contains no groups, findall returns a list of whole matches. When brackets are present, it assumes the groups are what was wanted and returns those instead, as one tuple per match.

There are two solutions. If the individual pieces are not needed, remove the brackets; if the brackets are needed only for grouping, make them non-capturing with (?:...).

Substitution

regex.sub replaces whatever the pattern matches. Groups extend what substitution can do: \1 and \2 in the replacement text refer to whatever group 1 and group 2 matched.

The following converts a date from Indian format into ISO format:

regex.sub(r"(\d{2})/(\d{2})/(\d{4})", r"\3-\2-\1", "Exam on 15/03/2026.")

# 'Exam on 2026-03-15.'

The day, month, and year are captured and then written back in a different order, without any parsing or explicit loops.

Operations of this kind are frequent in Unit I, where we clean text into a consistent form before any further processing.

A worked example: a small extractor

So far we have applied one pattern at a time. Information extraction, the term introduced in session 1, generally means pulling several fields out of every line and returning a structure a program can use.

The following three lines come from an invoice log. The fields are the same in each line, but the formatting varies:

INV-2291  15/03/2026  Rs 12,500  paid
INV-2292  16-03-2026  Rs 900     due
INV-2293  17/03/2026  Rs 1,05,000 due

There are four fields: an invoice number, a date, an amount, and a status. We build the pattern one field at a time:

INV-\d{4}              invoice: three letters, a dash, four digits
\d{2}[/-]\d{2}[/-]\d{4}   date: either separator — from the alternation section
Rs\s[\d,]+             amount: digits and commas, so 1,05,000 survives
paid|due               status: one word or the other

We join these with \s+ to allow for the gaps between fields. One further feature is useful here: instead of numbering the groups, we can name each one using (?P<name>...).

pattern = (r"(?P<invoice>INV-\d{4})\s+"
           r"(?P<date>\d{2}[/-]\d{2}[/-]\d{4})\s+"
           r"Rs\s(?P<amount>[\d,]+)\s+"
           r"(?P<status>paid|due)")

for line in lines:
    m = regex.search(pattern, line)
    print(m.group("invoice"), m.group("date"), m.group("amount"), m.group("status"))

# INV-2291 15/03/2026 12,500 paid
# INV-2292 16-03-2026 900 due
# INV-2293 17/03/2026 1,05,000 due

Named groups are worth the additional characters. m.group("amount") remains readable months later, whereas m.group(3) does not, and the numbered form breaks without warning as soon as a field is added in the middle of the pattern.

All the named groups can be retrieved at once:

regex.search(pattern, lines[0]).groupdict()

# {'invoice': 'INV-2291', 'date': '15/03/2026',
#  'amount': '12,500', 'status': 'paid'}

This dictionary is the goal of the exercise: unstructured text goes in, and structured data comes out.

Extraction is followed by normalisation

'12,500' is still a string, and the two dates are still in different formats. Extraction produces the pieces; they almost always require cleaning afterwards:

int(m.group("amount").replace(",", ""))     # 12500 — a number at last

regex.sub(r"(\d{2})[/-](\d{2})[/-](\d{4})",
          r"\3-\2-\1", m.group("date"))     # '2026-03-15' — one format

Find, extract, then normalise. This sequence recurs in every lab in the unit.

Exercise

Add a fifth field to the pattern. The log gains a customer code at the end, like [CUST-4471] — square brackets included.

Two points require care: the brackets are literal characters, and they should not appear in the captured value.

\[(?P<customer>CUST-\d{4})\]

Both brackets must be escaped, as \[ and \], because [ otherwise begins a character class. Omitting the backslash makes the pattern either invalid or wrong.

Placing the named group inside the escaped brackets keeps the brackets out of the captured text, giving CUST-4471 rather than [CUST-4471]. The position of the group determines what is returned.

Summary

The main points

Quantifiers are greedy by default, consuming as much text as they can. When a pattern matches considerably more than expected, this is almost always the reason.

Adding ? makes a quantifier lazy. Better still is to write the pattern so that it cannot overshoot at all.
