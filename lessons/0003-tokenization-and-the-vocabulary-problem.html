Tokenization

How a computer splits text into words, and why that turns out to be a difficult problem.

What tokenization is

Before a computer can do anything with text, it has to break the text into pieces. Those pieces are called tokens. This step is called tokenization.

The task appears straightforward: split the text on spaces.

"the cat sat"   →   ["the", "cat", "sat"]

This works for the sentence above. It stops working almost immediately afterwards.

Why splitting on spaces fails

Consider the following sentence:

"Dr. O'Neill isn't in — he's at St. Mary's, re: the U.S.A. deal."

Splitting on spaces produces several problems immediately:

  • Mary's, retains the comma, which is not part of the name.
  • isn't remains a single piece, although it represents two words, is and not.
  • Dr. and U.S.A. contain full stops. Splitting on full stops to fix the first problem would break these.

Each rule added to fix one case breaks another. After a while it can seem that the whole approach is unworkable.

It is not. Careful rules do eventually succeed, and the next section presents the standard ones. They settle only the punctuation, however. Underneath lies a second problem that no amount of rule-writing addresses, and that problem is the main subject of this session.

Rule-based tokenization

Adding rules one counter-example at a time is slower than it looks, but it does converge. Researchers did exactly this for years, and the result is a rule set that handles almost everything in ordinary English text. The best known is the Penn Treebank tokenizer, a collection of hand-written regular expressions of the kind we saw in sessions 1 and 2. Jurafsky & Martin, SLP3 §2.8, "rule-based tokenization". §2.7 shows the same job done with plain Unix tools, which is worth ten minutes of your time.

We do not write such a tokenizer ourselves; we call an existing one. Here is NLTK's version, applied to the same difficult sentence:

from nltk.tokenize import word_tokenize

word_tokenize("Dr. O'Neill isn't in — he's at St. Mary's, re: the U.S.A. deal.")

['Dr.', "O'Neill", 'is', "n't", 'in', '—', 'he', "'s", 'at', 'St.',
 'Mary', "'s", ',', 're', ':', 'the', 'U.S.A.', 'deal', '.']

Comparing this output against the three problems from the previous section, we see that the tokenizer handles all of them:

  • Dr. and U.S.A. retain their full stops, since the tokenizer recognises abbreviations.
  • The final . becomes its own token, since that one is genuinely punctuation.
  • isn't becomes is + n't, so the negation remains visible as a separate token.
  • Mary's becomes Mary + 's, with the comma as a separate token.

Punctuation becomes its own token rather than being deleted. This is the appropriate default: a question mark carries real information, and it can always be discarded later.

Use an existing tokenizer

For English text, rule-based tokenization is a solved problem, and there is no reason to write one by hand. NLTK's word_tokenize and spaCy's tokenizer both incorporate decades of accumulated counter-examples. We use both in lab 3.

What does matter is understanding what the tokenizer has done, since the tokens it returns are what every count in Unit II counts.

We can now give a partial answer to the question of where a word ends. For English prose, a word ends roughly where the spaces and punctuation suggest, and a good library knows the exceptions. This answer is useful, and it is the one we rely on throughout Unit I.

It is not sufficient for Unit III, however, and the reason has nothing to do with punctuation.

The vocabulary problem

What we mean by a "model"

This term is about to appear frequently, so we define it here. The full details are not needed yet, only enough to follow the argument that follows.

In sessions 1 and 2 we wrote rules by hand. We decided that a date looks like \d{2}/\d{2}/\d{4} and wrote that pattern out, and the computer applied it.

A model works the other way round. We do not write the rules. We supply a large collection of examples, a process called training, and the model derives the patterns itself. We then give it a new input and it produces a prediction.If you want a fuller answer now, the gentlest one on the internet is Google's "What is Machine Learning?" — about 20 minutes, no mathematics. Their ML Glossary is a good place to look up any term that appears before we teach it. Neither is required reading. We build all of this properly from session 20 onward.

To do this, a model must store some numbers for each word it knows, and it adjusts those numbers as it learns. For present purposes this is all the term needs to mean: a program that has learned from examples, and that keeps some numbers for every word it knows.

You will build your first model in week 6. For now, the important part is the storage of numbers per word, on which the rest of this lesson depends.

Every model in this course needs a vocabulary. That is a fixed list of every token the model knows. The model builds this list once, from its training text, and then it is fixed forever.

The list must be fixed because the model keeps a row of numbers for every token in it, which is the "numbers per word" from the definition above. Ten thousand words require ten thousand rows, so the size of the list determines the size of the model.

The difficulty is that language has no fixed word list. New words are coined continually: doomscrolling, rizz, ChatGPT-ing. However much text a model is trained on, it will encounter new words afterwards.

The model therefore fails in the following way:

training:  vocabulary = every word seen in the training text
later:     model sees "doomscrolling"  →  not in the list  →  <UNK>

<UNK> stands for "unknown word". Every word the model has not seen becomes this same token, so the model cannot distinguish doomscrolling from any other unknown word; they are all identical as far as it is concerned.

There is a further loss. doomscrolling contains scroll, a word the model knows well, so part of the meaning is available in the letters themselves. Splitting on spaces discards it.

Exercise

Suppose the word list is fixed, language continues to produce new words, and <UNK> is not available. What can be changed?

The pieces can be made smaller than words.

If the list holds word parts, any new word can be spelled out of parts already in the list. Taken to the extreme, a list of single letters can spell every word that exists.

Single letters, however, carry no meaning individually: the letter s means nothing on its own, and sentences become very long sequences of letters.

There is therefore a trade-off. Large pieces carry meaning but fail on new words; small pieces cover everything but carry little meaning. The solution is to choose pieces of intermediate size, which is what the next section describes.

Byte-Pair Encoding

We want word parts, but something must decide where the splits fall. A linguist could mark every prefix and suffix in English by hand, but this would take years and would not transfer to other languages.

Byte-Pair Encoding (BPE) instead learns the pieces by counting. The procedure is as follows:

  1. Start with a list of single characters.
  2. Count every pair of neighbouring symbols in your text.
  3. Take the pair that appears most often. Join it into one new symbol. Add that symbol to the list.
  4. Repeat k times.

That is the entire algorithm. k is a parameter we choose, and it determines the size of the final list.

A worked example

Consider the following small set of words. The number on the left is the frequency of each word, and _ marks the end of a word.

5  l o w _
2  l o w e s t _
6  n e w e r _
3  w i d e r _
2  n e w _

list:  _, d, e, i, l, n, o, r, s, t, w

We now count the pairs. The pair e r appears in newer (6 times) and in wider (3 times), giving a total of 9, which no other pair exceeds. We therefore merge it:

merge 1:  e + r  →  er

5  l o w _
2  l o w e s t _
6  n e w er _
3  w i d er _
2  n e w _

Counting again, er _ now appears 9 times, with no tie, so we merge it. Next n e appears 8 times (6 + 2), and we merge that. Continuing in this way:

Ties between pairs

Two pairs sometimes tie for the highest count. This occurs three times in the example above:

merge 1   e r  and  r _   both 9
merge 3   n e  and  e w   both 8
merge 5   l o  and  o w   both 7

We take the left-hand pair in each case.

The instruction "take the most frequent pair" does not specify what to do when two pairs tie, and the choice does not matter. A real implementation applies some fixed rule so that the same input always produces the same output, and either choice leads to a reasonable vocabulary. If a hand-worked trace diverges from ours at a tie, check the counts and then continue with your own choice.

merge 2:  er + _  →  er_
merge 3:  n + e   →  ne
merge 4:  ne + w  →  new
merge 5:  l + o   →  lo
merge 6:  lo + w  →  low

5  low _
2  low e s t _
6  new er_
3  w i d er_
2  new _
What the algorithm has learned

The algorithm has created the symbol er_. In English, -er at the end of a word indicates a comparative: wide becomes wider. This is a genuine element of English morphology, the subject introduced in SLP3 §2.2.

None of this was supplied to the algorithm. It has no representation of English and performs only frequency counting. The morphological unit emerges from the counts.

The algorithm has also determined that low and new are frequent enough to remain whole. In general, frequent words stay in one piece and rare words are split into parts.

Why this solves the vocabulary problem

Consider the word lower, which does not appear in the training list above. The whole-word approach would represent it as <UNK>.

BPE splits it into low + er_, both of which are already in the list. The model knows low, and it knows what er_ contributes to a word, so it can represent lower despite never having seen it.

There are thus no unknown words. This is the central property of the method: any word encountered later can be spelled out of pieces already in the list, falling back to single characters if necessary.

Unknown characters are a separate matter. A character that never appeared in training, such as a script the model has not seen or a new emoji, is also absent from the list, and <UNK> returns. This is a genuine limitation, and it is why GPT models apply BPE to bytes rather than characters. There are only 256 possible bytes, all present in the list from the outset, so nothing can be unknown. The algorithm is the same, applied one level lower.

Question 1 of 2

What happens if you increase k, the number of merges?

Correct answer: bigger list, fewer tokens.

Each merge adds one new symbol to the list, so more merges give a larger list.

Each merge also replaces two symbols with one, so the same text requires fewer tokens to represent.

This is the trade-off. A large list gives short token sequences but a large and slow model; a small list gives a small model but long token sequences. Both cannot be optimised at once. Real systems generally settle on a vocabulary of roughly 30,000 to 50,000 tokens — BERT has 30,522 and GPT-2 has 50,257. (The merge count is a little lower than that, because the starting characters are in the list before any merging happens.)

Question 2 of 2

Why does BPE mark the end of each word with _?

Correct answer: so merges cannot run past the end of one word.

Without the marker, BPE would count the last letter of one word together with the first letter of the next as a pair, like any other. If that pair were frequent, the two would be merged, producing symbols that span a word boundary and correspond to nothing.

The marker has a second use. Because er_ and er are distinct symbols, the original text can always be reconstructed exactly, including its spaces. This matters for any model that must generate text, as we see in Unit III.

When we use BERT in Unit III, its tokenizer produces output of the following form:

"doomscrolling"  →  ["doom", "##scroll", "##ing"]

The ## prefix indicates that a piece attaches to the one before it. It carries the same information as the _ in our example but marks the opposite end: _ indicates where a word finishes, whereas ## indicates that a piece is a continuation of the previous one. Either convention distinguishes word boundaries from word-internal positions, which is what matters.

Summary

The main points

Tokenization is not simply a matter of splitting strings. It determines the units a model is able to represent. If we choose whole words, new words become unknown; if we choose word parts, the model can represent any word it encounters.
