Searching a collection

The term-document incidence matrix, how Boolean queries are answered with it, and the reason it does not scale to real collections.

Everything so far worked on one text

Tokenization, tagging, named entity recognition — all of it operated on a single piece of text. Now: given a whole collection, which documents match what we are looking for?

This is information retrieval, and it is what a search engine does.

The simplest useful form of search

Brutus AND Caesar AND NOT Calpurnia

Over the plays of Shakespeare: the plays containing both Brutus and Caesar but not Calpurnia. The question is how to answer it quickly over a large collection.

Scanning every document is not enough

  • What Ctrl-F and grep do — fine for one file
  • Far too slow for a large collection: every document is re-read on every query
  • NOT and complex combinations are handled awkwardly
  • No basis for ranking results later

We want the collection organised in advance, so that queries are fast.

A table with one row per term and one column per document. Each cell is 1 if the term appears in that document and 0 if it does not.

Each row is a string of 0s and 1s — a bit vector — recording exactly which plays contain that word.

The Caesar row is 1 1 0 1 1 1: the word appears in every play except The Tempest.

The query becomes bitwise arithmetic

Brutus            1 1 0 1 0 0
Caesar            1 1 0 1 1 1
NOT Calpurnia     1 0 1 1 1 1     <- Calpurnia was 0 1 0 0 0 0, flipped

Brutus AND Caesar             ->   1 1 0 1 0 0
        AND NOT Calpurnia     ->   1 0 0 1 0 0

AND keeps a 1 only where both rows have a 1; NOT inverts every bit.

The 1s are in columns 1 and 4

result:   1 0 0 1 0 0

          Antony and Cleopatra     Hamlet

Every Boolean query reduces to a few bitwise operations on rows, and those are among the fastest operations a computer performs.

Antony   1 1 0 0 0 1

AND      1 0 0 0 0 1

The 1s are in columns 1 and 6: Antony and Cleopatra and Macbeth. The two words occur together only in those plays.

The method itself is sound. The difficulty is the size of the table.

Terms run down one axis and documents across the other, so the matrix grows with both.

The figures for a realistic collection

  • 1 million documents — the columns
  • about 500,000 distinct terms — the rows
  • 500,000 × 1,000,000 = 500 billion cells, half a trillion 0s and 1s to store

What those cells contain

Each document has perhaps a thousand distinct words, so each column holds about a thousand 1s and 499,000 zeros. Out of 500 billion cells, at most about a billion are 1s.

That is 99.8% zeros. Almost all the memory would record that words are absent — nearly always true, and rarely what the query asks about.

The incidence matrix has the right idea — organise the collection in advance so queries are fast — in the wrong representation.

What needs to change is how the table is stored, not how queries are answered.

Exercise

Work it out before the next session

Almost every cell is a 0, and those 0s carry no information we need. What should be changed?

Stop storing the zeros. Record only the 1s.

For each term, keep a list of the documents it actually appears in. That list is short, because a given word occurs in few documents, and no space is spent on absence.

This structure is the inverted index: session 9, and the structure built in lab 4.

Question 1 of 2

In a term-document incidence matrix, what does a single row represent?

Correct: one term, as which documents it appears in.

Rows are terms, columns are documents. The Caesar row, 1 1 0 1 1 1, records that Caesar appears in every play but the third. A Boolean query combines these rows bitwise.

Question 2 of 2

What is the main problem with the incidence matrix at real scale?

Correct: it is almost all zeros, so it wastes nearly all its space.

A million documents by half a million terms gives 500 billion cells, of which at most a billion are 1s. The bitwise operations are fast; storing all that absence is what makes the approach impractical.

Summary

The incidence matrix reduces Boolean search to fast bitwise operations on rows of 0s and 1s, and it is correct. At realistic scale it is 99.8% zeros and does not fit in memory.

Next: store only the 1s. That structure is the inverted index.
