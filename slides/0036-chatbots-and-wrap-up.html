Chatbots, and the course wrap-up

A task-oriented chatbot fills a frame. Then the table session 22 left standing, extended to the rest of the course.

The syllabus clause is the application. The calendar also gives this sitting the wrap-up: the argument the other thirty-five sessions built.

A traveller wants a flight. A system that books it has to know where from, where to, and when.

SLP3 Appendix K calls the structure that holds those facts a frame: a collection of slots, each taking a set of possible values. The job is to fill the slots and then act. The architecture is 1977 — GUS, a travel-planning system whose frames became the industrial pattern for thirty years.

Filling that frame from an utterance

  • Domain classification — which frame are we in? Airlines, an alarm clock, a calendar
  • Intent determination — what general task is the user trying to accomplish? Show a flight, set an alarm, remove an appointment
  • Slot filling — extract the particular values the utterance supplies

The first two together decide which frame we are filling.

One sentence, all three jobs

Show me morning flights from Boston to San Francisco on Tuesday

Two fine-tuning recipes sharing an encoder

Session 33 sat the sequence classifier on [CLS]; Appendix K sits it on EOS. One designated position carries the whole-sequence label — a convention, not a law.

A working system wraps a small loop around that extractor: ask questions until the slots are full, query a database, report back, using templates for the replies. Dialogue acts, state tracking and sentence realisation are the rest of Appendix K, and not this clause.

Exercise

(a) then (b)

(a) book me a flight to Bengaluru on Tuesday morning — which part is the intent, which are slots, and which session taught each?

(b) I need to be in Bengaluru for a meeting on Wednesday morning. Which slots can the tagger fill?

(a). Intent SHOW-FLIGHTS or BOOK-FLIGHT, from a whole-sequence head — session 33, equation (10.11). Slots DESTINATION-CITY = Bengaluru, DEPARTURE-DATE = Tuesday, DEPARTURE-TIME = morning, via BIO tagging — sessions 7 and 33, equation (10.12).

(b). Destination, yes. Departure date — there is no token to tag. The intended answer is Tuesday, and it comes from knowing that people arrive the day before a meeting, not from the sentence. Same machinery as (a), and it has just run out.

Appendix K evaluates two ways, and they are session 14's names.

Task success rate is extrinsic — the percentage of times the system booked the right flight, the only thing the user cares about, and it needs a whole dialogue to measure. Slot error rate is intrinsic: "a more fine-grained, but less extrinsic metric."

K.1.3's confidence thresholds

the system's confidencewhat it does

Explicit confirmation makes errors easy to correct and is, K says, "time-consuming and awkward".

Session 34 closed on §12.7: systems need confidence values so they can abstain from translations that may cause harm. Knowing when not to answer was the open problem that chapter named.

A frame-filler from 1977 and a translator from 2026 have the same problem — and the course can say so because session 34 already named it.

Three architectures in one sequence: frames and slots, this session → retrieval-augmented generation, session 35 → instruction tuning and alignment, chapter 9.

The course covers the first two. The third is the chapter it names and stops at.
Question 2 of 2

Why can a task-oriented chatbot not answer an open-domain question?

Correct: the frames are defined in advance. Domain classification picks among known frames; slot filling extracts known slots. An open-domain question has no such frame. A structural limit, not a size one.

The second is a size explanation for a structural limit, which is the more instructive error. The fourth confuses a tagging scheme with a domain ontology — BIO will tag as many slot types as the label set contains; what it will not do is invent a slot the frame does not have.

The architectures will date

Three habits the course kept finding will not.

Session 26 counted four: session 18's idf against the Shakespeare features, session 21's king−man+woman landing on king, session 22's GloVe against Word2Vec, session 26's LSTM against GRU in a paper two of the GRU's authors signed.

Session 32 made next-sentence prediction the fifth, and said so. Session 34 ran the same move without numbering it: the easy claim is that MT reflects its training data; Prates et al. found amplification. The habit is more durable than any of the results.

Every session in Unit III closed on a limitation, and each limitation was the next session's subject.

This session's own limitation — the meeting that implies a flight date — is the last one, and it has no next session. Chapter 9 is the pointer, not the patch.

Perplexity, chrF, token F1 — and now slot error rate.

Intrinsic evaluation is inexpensive and approximate; extrinsic evaluation is expensive and definitive. Session 34 restated that trade for translation; K.0.2 uses it almost verbatim, twenty-two sessions after session 14 taught it. Lab 6 remains the reference for precision, recall and F1.

Session 1 promised five applications and a way of turning language into numbers a machine can compare. The five landed.

The numbers ran from one bit per word to a contextual vector per occurrence, and then to a generator conditioned on documents the weights never saw. And knowing when not to answer is still open, for the oldest architecture in this hour and for the newest alike.

Summary

A frame is a collection of slots; filling it is domain classification plus intent determination plus slot filling. Intent is session 33's sequence classification; slots are session 7's BIO tags. Fig. K.3 does both on one encoder, with the whole-sequence label on EOS rather than [CLS].

Slot error rate is intrinsic, task success extrinsic, and confidence thresholds decide when to reject, confirm or act. Session 22's six representations extend by four, and the three debts it named are paid. Chapter 9 is named and not taught.
