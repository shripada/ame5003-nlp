MSIS · AME 5003 · Unit I · Session 04

Cleaning up text

Normalization and stop words: deciding which differences do not matter, and removing them.

Session 3 gave us a list of tokens

"US"    "us"    "U.S."    "Us"

A reader treats some of these as the same word. To the computer they are four different strings, with nothing connecting them.

Normalization

Normalization deliberately destroys information we have judged to be irrelevant.

The difficulty is judging which differences are irrelevant, and that depends on the task.

Case folding (lowercasing)

"AMAZING"   "Amazing"   "amazing"

        ->   "amazing"

Case folding makes three strings one, so every capitalisation is counted together. For counting and searching, this is what we want.

What lowercasing merges

  • US the country and us the word — now one token
  • Apple the company and apple the fruit
  • Polish from Poland and polish for shoes

In each case the capital letter carried real meaning, and lowercasing discarded it.

Exercise

Think first

We are building a system to extract company names from news articles, and the first step is to lowercase everything.

What has this broken?

It removes the main clue available. A capital letter in the middle of a sentence is a strong sign that a word is a name — Apple, Rao, Manipal.

The same step that helps a search system harms this one. There is no normalization that is correct in general, only normalization that is correct for a particular task.

Two strings that look identical

a = "café"     # é stored as ONE character
b = "café"     # é stored as  e + a separate accent

a == b    ->    False
len(a)    ->    4
len(b)    ->    5

Unicode gives two ways to store the same character

FormStored asLength
precomposedc a f é (U+00E9)4
decomposedc a f e (U+0065) + combining acute (U+0301)5

They print the same. If a user types one form and the stored text holds the other, the lookup fails and nothing reports an error.

Convert both to one standard form first

normalize("NFC", a) == normalize("NFC", b)

        ->    True

This is Unicode normalization. The usual choice is NFC (Normalization Form C).

Why this matters for Indian scripts

Indian scripts are built from base letters plus combining marks, so the same Kannada word can arrive in two encodings that look identical and compare as unequal.

This belongs to the same family as the regex-versus-re issue in session 2: Indian text has structure that naive handling gets wrong. One rule covers both cases — use regex to split and NFC to compare.

Punctuation, numbers, and accents

  • Punctuation — strip it to count words; keep it to find sentence boundaries, or to read emoticons in a review
  • Numbers — replace with <NUM> when the value does not matter; keep it for prices, dates and amounts
  • Accents and spelling — résumé → resume, colour → color

There is no fixed procedure. Every one of these steps asks the same question:

for this task, is the difference noise or signal?

Stop words

  • Stop words are very common words carrying little content — the, is, of, a, and
  • They appear in almost every sentence, so each one says little about the topic
  • Ready-made lists exist; NLTK's English list holds about 200 words

Removing them amounts to keeping only the tokens that are not on the list.

Removing them for search

"this is one of the best phones I have ever bought"

        ->  "best phones ever bought"

The words that remain are the ones that carry content. There is less to store, and the informative words stand out, which is what information retrieval wants.

Now look at what the list contains

not    no    nor    against    only    very

Every one of these changes the meaning of a sentence, including not, which is the word a negative judgement usually turns on.

The same step, on a product review

“would not recommend”

“would recommend”

The meaning is now reversed, and a sentiment system would read a negative review as positive. VADER failed on nightmare in lab 1 for the same reason: a routine preprocessing step removed the information the task depended on.

When to remove them, and when not to

TaskWhy
RemoveSearch, information retrieval, topic Function words are noise; we want the keywords. This is lab 4.
KeepSentiment, question answering Meaning depends on them. “To be or not to be” is entirely stop words.

Modern systems remove fewer stop words than older ones did — the models can now use these words rather than being confused by them.

Question 1 of 2

Why does lowercasing a document count as destroying information?

Correct: case can carry meaning, and merging it cannot be undone.

Once US and us have both become us, nothing says which was which. That is acceptable when the distinction was noise, and a real loss when it was signal.

Question 2 of 2

For which task is removing stop words most likely to be a mistake?

Correct: deciding whether a review is positive or negative.

Sentiment is carried by exactly the words the list discards — not, no, very. The other three depend on content words, so removing function words helps them.

Summary

Every cleaning step discards information on purpose. Whether that helps or harms depends entirely on the task, so there is no single correct way to clean text.
